# Architecture

Authentication extends sessions with transactional signup, one-hour Django reset tokens and django-allauth Google/GitHub/Microsoft callbacks. Public auth writes require CSRF; PostgreSQL counters rate-limit attempts across workers. Auth pages use browser paths, while business sections retain hashes. Provider UID identifies returning users; email does not automatically merge accounts. New users receive personal workspaces; company assignment stays local. See [authentication.md](authentication.md).

Browser → React + TypeScript → Vite proxy `/api` → Django 5.2 / DRF → PostgreSQL 18. Two development processes share one application database. Django provides the ORM, migrations, password hashing, sessions, and CSRF protection.

`backend/config/settings/` contains shared, local, and test settings; tests also use PostgreSQL. `backend/apps/` contains accounts, clients, deals, invoices, and analytics. Accounts owns Workspace, WorkspaceMembership, user provisioning, session authentication, and the trusted employee assignment command. `backend/common/` contains error handling, health checks, and workspace access checks. The repository follows the detailed tree in section 13.2 of the technical plan.

Workspace, WorkspaceMembership, Client, ClientNote, ClientLink, Deal, Invoice, and InvoiceItem use UUIDs. A user has one workspace membership. Client, Deal, and Invoice belong to a workspace and preserve the original owner as created_by for audit purposes. Child objects inherit workspace through their parent: notes/links through Client, and items through Invoice. A note author and a record creator must belong to the relevant workspace. Amounts use NUMERIC/Decimal, and dates use timezone-aware UTC values. Related business records use PROTECT.

The Clients API supports CRUD, search, pagination, validation, and controlled deletion alongside the health/auth APIs. A workspace-scoped queryset is applied before list filtering or object lookup. Object permissions verify the workspace again. The API sets workspace and created_by from the authenticated account; input cannot override them. Missing membership fails closed with 403; foreign objects return 404. All employees of one workspace have the same client permissions. Client writes lock membership within a transaction to serialize against the local assignment command.

Database constraints enforce one membership per user, unique workspace/user pairs, valid statuses, nonnegative amounts, invoice_number uniqueness per workspace, and status/paid_at consistency. Cross-workspace relationships and immutable workspace/created_by fields are validated during regular model.save() calls. QuerySet.update(), bulk_create(), and direct SQL bypass model validation and must not change ownership or relationships. Future child APIs must scope through their parent workspace.

The frontend provides session sign-in, hash navigation, shared design tokens, persisted System/Light/Dark appearance, and global quick actions in a responsive sidebar layout. The session DTO supplies the signed-in user's workspace name for navigation and Settings; this is read-only display data. Clients is connected to the workspace-scoped API for list/search/reset/pagination, create/edit, read-only related-deal details, and confirmed deletion. It uses the shared fetch client, never accepts a workspace selector, resets on account change, and refetches after writes or explicit Refresh. Native dialogs manage keyboard focus and preserve the mounted list. See [project-structure.md](project-structure.md) for component responsibilities.

Nested notes/links APIs resolve their parent through the same workspace-scoped client queryset and lock membership and parent on creation. Notes receive their author from the session; timestamps are server-controlled. History is chronological and paginated. Only the author may delete a note; membership, parent, and note are locked for that operation. The server supplies can_delete as a UI hint and independently enforces authorship. Links have no edit/delete operation. The drawer loads notes and links independently and refetches after confirmed writes/deletions. Note content is plain text, and external links accept only http/https and open without opener/referrer access. There are no realtime updates or separate comment roles.

Dashboard, Deals, and Invoices remain placeholders. Deals/Invoices CRUD, optimistic locking, invoice calculations, automatic paid_at updates, PDF, analytics, and full business-flow E2E tests are not implemented. Documentation, interface copy, and application messages use English.

# Decisions and clarifications

Authentication uses django-allauth for provider protocol/state/PKCE processing while preserving existing users, sessions and CSRF. Only the project API and provider callbacks are exposed; alternate account-management pages are not added. Public password/social signup is transactional and serialized by normalized email. Provider UID determines identity, email collisions require explicit connection, recent verification gates method changes, and user locking protects the last method. Auth counters use PostgreSQL rather than per-process cache. Local email uses console output; production settings require SMTP/HTTPS, without claiming live delivery or deployment.

- The detailed tree in section 13.2 refines the shorter tree in section 3: Django modules live in `backend/apps/`.
- Keep standard Django users and sessions. New users register/sign in by email; legacy username login remains compatible. Ambiguous legacy emails cannot select an arbitrary user. Signup and password recovery are implemented without rewriting existing email identities.
- Company records belong to Workspace, and employees share access through WorkspaceMembership. OneToOne(user) enforces at most one workspace per user in PostgreSQL; normal user creation provisions membership. There are no team roles, invitations, billing, or public membership APIs.
- Legacy owner fields are renamed to created_by instead of discarded, preserving record provenance. Workspace controls access; created_by does not restrict colleagues. Workspace and creator are immutable through normal model saves and Clients CRUD.
- Existing users receive separate workspaces during data migration. Automatic grouping by company name is unsafe. The local assign_workspace command moves only users whose source workspace contains no business records. Existing data transfers require separate review; no automatic company merge is provided.
- ClientNote and ClientLink inherit workspace through Client; InvoiceItem inherits it through Invoice. Note authors may be any member of the client's workspace. Client, Deal, and Invoice have explicit workspace foreign keys, and financial invoice numbers are unique per workspace.
- Legacy ownership inconsistencies abort the data migration. Initial migrations are unchanged; staged additions, owner renames, data backfill, and required fields form the upgrade path. Reverse data migration is intentionally unsupported because shared company data cannot safely become private records again. Recover from a backup if necessary.
- Client deletion returns 409 when any protected related record exists, including invoices, deals, notes, and links. A note's author may explicitly delete that note after confirmation; colleagues cannot delete it. Separate deletion workflows for links, deals, and invoices are not implemented.
- Client input permits only name, company, email, and phone. Read-only, ownership, and unknown fields are rejected with 400 instead of silently ignored. Phone remains a free-form contact string up to 50 characters; email uses DRF/Django format validation. No national phone format is imposed.
- Clients list uses DRF SearchFilter on name/company/email, ordering by created_at descending then UUID descending, and page-number pagination (20 by default, configurable page_size capped at 100). The established routes have no trailing slash.
- The original requirements show money as JSON numbers; the technical plan specifies Decimal strings. Future financial APIs must return strings without using JavaScript Number for calculations.
- Initial models use 2 decimal places for amounts, 3 for quantity, and 4 for tax_rate. Currency codes are validated as three uppercase Latin letters; the ISO code registry and support for currencies with different decimal precision need clarification before financial services are implemented. Amounts in different currencies must not be combined.
- Archived does not automatically mean lost. Outcome supports none/lost/cancelled and may differ from none only for archived deals. Paid requires paid_at; initial models validate this, while automatic timestamps belong to status transition services.
- Invoice stores buyer_snapshot/seller_snapshot and monetary totals. Snapshot creation, item calculations, rounding, and protection against changes to historical data will be implemented with the invoice module. Financial writes are not available through the API until then.
- Revenue from paid invoices, Win Rate based on paid and archived/lost deals, tax rules, and the legal invoice format remain assumptions in the technical plan. Confirm them before implementing their respective modules.
- The existing PostgreSQL cluster is used without reinstallation or reinitialization. Separate micro_crm and test_micro_crm databases isolate application and test tables. The application role has no superuser/CREATEDB/CREATEROLE privileges; an administrator precreates the test database, and pytest preserves it between runs.
- The security directory contains policies and checks rather than duplicating Django permissions. Root-level tests/ is reserved for future end-to-end and cross-module scenarios; current tests live in backend/tests/ and frontend/tests/.
